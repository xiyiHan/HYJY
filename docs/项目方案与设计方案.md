## 一、项目背景与目标

### 1.1 现状

命令行版会议纪要工具已完成开发并在一场真实会议（47 分 47 秒，大同市中心血站调研）上完成端到端验证：本地转写 → 云端生成纪要 → 填充单位正式模板，60 项自动化测试全部通过。

目前的使用方式是命令行：`python mm.py run 录音.m4a --project "..."`。对使用者而言存在三个障碍：

1. **要记命令**。11 个子命令、若干参数，不常用就会忘，需要回到文档查。
2. **过程不可见**。47 分钟的音频要转 17 分钟，期间只有一个百分比进度，无法判断是在正常工作还是卡住了。
3. **换电脑要重新搭环境**。装 Python、建虚拟环境、装依赖、下模型，步骤多且易错。

### 1.2 目标

| 目标 | 具体标准 |
| --- | --- |
| 易用 | 双击图标即用，常用流程不超过 3 次点击；无需记忆任何命令 |
| 可迁移 | 换一台电脑后，从零到可用不超过 2 步操作 |
| 可分发 | 能打包成可交付物，交给同事时对方不需要懂 Python |
| 可维护 | 代码纳入 Git 版本管理，变更可追溯、可回滚 |

### 1.3 范围界定

**本期做**：图形界面、环境自检与一键安装、配置可视化管理、打包与分发方案、Git 版本管理。

**本期不做**（列入远期）：
- 多人协作与权限体系
- 服务端部署、网页版多人访问
- 移动端
- 语音模型微调

## 四、总体方案

### 4.1 架构设计

核心思路：**前后端分离，界面只管交互，业务逻辑完全复用现有模块。**

```
┌─────────────────────────────────────────────┐
│  表现层  PySide6 桌面窗口                     │
│  任务页 / 结果页 / 设置页 / 日志             │
└──────────────────┬──────────────────────────┘
                   │ 信号槽（不阻塞界面）
┌──────────────────▼──────────────────────────┐
│  任务调度层  后台线程 + 进度回报 + 取消      │
│  把原命令行流程包装成可观察、可中断的任务     │
└──────────────────┬──────────────────────────┘
                   │ 直接调用，不改动
┌──────────────────▼──────────────────────────┐
│  业务层（现有 mmtools，零改动复用）          │
│  转写 / 纪要 / 模板填充 / 术语表 / 录音      │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│  运行环境层  虚拟环境 + 模型 + 配置          │
│  可重建、可迁移、可自检                      │
└─────────────────────────────────────────────┘
```

**关键设计点**：业务层不引入任何界面依赖。这样命令行版可以继续使用，界面出问题时还能退回命令行，也让核心逻辑可以独立测试（现有 60 项测试不受影响）。

### 4.2 GUI 技术选型

| 维度 | PySide6（Qt） | Gradio / Streamlit | Tkinter |
| --- | --- | --- | --- |
| 界面形态 | 原生桌面窗口 | 浏览器页面 | 原生，样式简陋 |
| 用户体验 | 最接近"软件" | 需开浏览器，像网页工具 | 一般 |
| 开发工作量 | 中 | 低 | 中 |
| 额外依赖体积 | 约 150 MB | 约 80 MB | 0（内置） |
| 常驻内存 | 约 120 MB | 约 250 MB（含服务进程） | 约 60 MB |
| 拖拽、进度、托盘等桌面特性 | 原生支持 | 受限 | 部分支持 |
| 打包成熟度 | 好 | 一般 | 好 |

**推荐 PySide6。** 理由：

1. 本项目对内存敏感（转写峰值 2.28 GB / 空闲 2.5 GB），Gradio 要多常驻约 130 MB，长期看是负担。
2. 用户要的是"双击就能用的软件"，浏览器页面在观感与操作习惯上都不达标（拖拽文件、最小化到托盘、任务栏进度等桌面特性 Gradio 无法提供）。
3. 由于分发方案不走单文件打包（见 4.3），150 MB 的依赖体积不构成额外成本。

> 备选：若希望**最快看到可用界面**，可先用 Gradio 做一版验证交互流程，再决定是否迁移到 PySide6。但两版并存会增加维护成本，不建议长期保留。

### 4.3 打包与分发方案

**先说结论：不要打成单个 exe。**

理由（有公开实践与本次实测共同印证）：

| 问题 | 具体表现 |
| --- | --- |
| 体积失控 | 把 PyTorch 打进 exe 会到 2~4 GB，解压要一两分钟 |
| 启动缓慢 | 每次启动都要解压到临时目录 |
| DLL 缺失 | 目标机若无 VC++ 运行库，直接报错闪退 |
| 路径陷阱 | 解压目录 `_MEIPASS` 会让模型/配置的相对路径全部失效 |
| 杀软误报 | 自解压行为常被判定为可疑，需代码签名证书（每年数百至数千元） |

**推荐三级分发方案，按需求递进：**

| 层级 | 形态 | 体积 | 适用场景 | 成本 |
| --- | --- | --- | --- | --- |
| **一级** | 源码 + 一键安装脚本 | 约 10 MB | 自己与身边同事使用；目标机可联网 | 低 |
| **二级** | 绿色便携包（嵌入式 Python + 依赖 + 模型） | 约 3 GB | 交给不懂技术的同事；目标机不联网 | 中 |
| **三级** | 单文件 exe | 约 800 MB | 远期，需先完成 ASR 引擎 ONNX 化 | 高 |

**一级方案（推荐落地）**

```
会议纪要工具/
├── 安装.bat          ← 双击：建虚拟环境、装依赖、下载模型、生成配置
├── 启动.bat          ← 双击：启动图形界面
├── app/              源码
├── requirements*.txt
└── README.md
```

安装脚本要点：
- 自动检测 Python（无则提示下载地址，或从内置目录取）
- 强制把 pip 缓存、临时目录、模型目录指向大盘，避免撑爆系统盘
- 装完自动跑一次环境自检并打印结果

**二级方案（便携包）**

用 Python 官方 embeddable 包（约 15 MB 的精简解释器）替代完整安装，配合离线 wheel 目录。优点是目标机完全不需要装 Python，解压即用；代价是约 3 GB 的体积，需要 U 盘或网盘传递。

**三级方案（远期，需要额外改造）**

把 FunASR 的 PyTorch 推理换成 ONNX Runtime。据公开实践，同样的语音模型走 ONNX 后，运行时从约 2.5 GB 降到约 45 MB，启动内存从 1 GB 降到 80 MB。这对本项目有两重价值：既能做小体积 exe，**也能显著缓解内存瓶颈**。

代价是要重新验证识别准确率，属于独立课题，建议列为下一阶段。

### 4.4 迁移方案

| 迁移内容 | 方式 |
| --- | --- |
| 代码 | Git 拉取 |
| 虚拟环境 | 目标机重新创建（脚本自动完成），不复制 |
| 模型 2.6 GB | 优先复制（快、省流量）；也可让脚本重新下载 |
| 配置 | 复制 `config.local.yaml`（含密钥路径与模板路径） |
| 业务数据 | 复制 `workspace/` 目录 |
| 录音文件 | 按需复制，注意涉密文件的传输合规 |

**必须做的一件事：硬件自适应。** 目标机若有独立显卡，应自动启用 CUDA 加速。目前 `faster_whisper` 支持 `device: auto`，`funasr` 还写死为 `cpu`，需要补上自动探测。

## 五、详细设计

### 5.1 界面设计

采用左侧导航 + 主内容区的经典桌面布局，四个页面：

```
┌────────────────────────────────────────────────────────────┐
│  会议纪要工具                          [环境状态 ●] [设置]  │
├──────────┬─────────────────────────────────────────────────┤
│          │                                                 │
│  ① 任务  │   拖入录音文件，或                               │
│          │   [ 选择文件 ]  [ 开始录音 ]                     │
│  ② 结果  │                                                 │
│          │   ┌───────────────────────────────────────┐     │
│  ③ 设置  │   │ 血站调研.m4a    47:47   等待中        │     │
│          │   │ 灵丘县调研.mp3  待分析  等待中        │     │
│  ④ 帮助  │   └───────────────────────────────────────┘     │
│          │                                                 │
│          │   [ 开始处理 ]        预计需要 25 分钟           │
├──────────┴─────────────────────────────────────────────────┤
│  转写中 ▓▓▓▓▓▓▓▓░░░░░░░░  第 3/8 批  ·  已用 6:20  ·  剩余 11:40│
└────────────────────────────────────────────────────────────┘
```

**① 任务页**

- 拖拽区支持一次拖入多个文件，自动排队
- 每个文件显示：文件名、时长、状态（等待中 / 转写中 / 生成纪要中 / 已完成 / 失败）
- 处理中显示当前批次与预计剩余时间（依据实测 2.8 倍速估算）
- 支持中途取消，已完成的文字稿保留

**② 结果页**

- 左侧文件列表，右侧显示生成的纪要预览
- 顶部三个按钮：[打开 Word 文件] [打开所在文件夹] [重新生成]
- 「重新生成」用于修改提示词或换模型后重跑，**不重新转写**（省 17 分钟）

**③ 设置页**

| 分组 | 项目 |
| --- | --- |
| 云端平台 | 平台选择（下拉）、API Key（密钥文件路径或直接填写）、连通性测试按钮 |
| 转写 | 引擎选择（FunASR / faster-whisper）、模型规格、热词编辑 |
| 纪要 | 模板文件路径（可浏览选择）、项目名称、建设单位/承建单位/监理单位全称 |
| 术语表 | 规则增删改，带"预演"按钮（不实际改动，先看效果） |
| 高级 | 缓存目录、批处理大小、日志级别 |

**④ 帮助页**

- 环境自检结果与一键修复
- 常见问题（密钥无效、模型下载失败、录音无声、内存不足）
- 操作说明与快捷键

### 5.2 关键技术设计

**后台任务不阻塞界面**

转写要跑十几分钟，必须放在后台线程，通过信号槽回报进度，否则界面会假死。设计要点：

- 任务对象暴露 `progress(stage, current, total, message)` 信号
- 支持协作式取消（在批次边界检查取消标志，不强行杀线程）
- 业务层不感知界面，进度通过回调函数注入

**配置的可视化编辑**

设置页写入的仍是 `config.local.yaml`，与命令行版共用同一份配置。这样两种使用方式不冲突，用户也可以随时手改文件。

**密钥处理**

沿用已有的"密钥文件路径"方案。界面只显示路径与脱敏后的密钥，不回显完整密钥，也不写入日志。

### 5.4 Git 版本管理设计

**仓库位置**：建议放在 D 盘。C 盘仅剩 5.8 GB，Git 的对象存储与工作区都不宜放在系统盘。

**`.gitignore` 要点**（.gitignore 本身必须提交）：

```gitignore
# 密钥与本地配置 —— 绝不入库
config.local.yaml

# 运行产物：含会议录音，可能涉密，绝不入库
workspace/
.cache/

# 模型：体积大，用脚本或复制方式分发
models/

# 虚拟环境
.venv/
venv/

# Python
__pycache__/
*.py[cod]

# 编辑器与系统
.vscode/
.idea/
Thumbs.db
```

**特别提示**：`workspace/` 里存的是真实会议录音与纪要，可能涉及项目信息甚至敏感内容。**务必确保它不在版本库中**，这一点要在首次提交前用 `git status` 逐项核对。

**分支策略**（单人项目，保持简单）：

| 分支 | 用途 |
| --- | --- |
| `main` | 稳定可用版本，随时可交付 |
| `dev` | 日常开发 |
| `feature/*` | 单个功能，完成后合并回 dev |

**提交规范**：采用 `类型: 简述` 格式，便于日后检索。

```
feat: 新增图形界面任务页
fix: 修正模板填充时会议主持字段填不进去的问题
docs: 补充部署说明
test: 为段落合并补充边界用例
```

**远程仓库**：需要确定托管位置。选项与差异：

| 方案 | 优点 | 注意 |
| --- | --- | --- |
| Gitee（码云） | 国内访问快，私有库免费 | 需实名 |
| GitHub | 生态最好 | 国内访问不稳定 |
| 单位内网 GitLab | 数据不出单位，最合规 | 需要单位提供 |
| 仅本地仓库 | 零依赖 | 无异地备份，硬盘损坏即丢失 |

> 考虑到项目属于单位业务系统，**内含单位名称、项目名称等业务信息**（虽已排除密钥与录音），建议优先考虑单位内网 GitLab；若无条件，用 Gitee 私有库。

## 六、实施计划

| 阶段 | 内容 | 交付物 |
| --- | --- | --- |
| **一、仓库初始化** | 建 Git 仓库、写 .gitignore、首次提交、配置远程 | 可正常提交与推送的仓库 |
| **二、界面骨架** | PySide6 主窗口、四个页面布局、配置读写打通 | 可启动的界面 |
| **三、核心交互** | 拖拽入队、后台任务、进度回报、取消 | 能完整跑通一次转写与纪要生成 |
| **四、配置与自检** | 设置页、环境自检、错误提示中文化 | 用户可自助完成配置 |
| **五、安装脚本** | install.bat / start.bat、新机验证 | 换机可 2 步部署 |
| **六、打包分发** | 便携包脚本（可选）、交付说明 | 可交付给同事的压缩包 |

**里程碑**：阶段三完成即可自用（这是价值最大的一步）；阶段五完成即可帮同事部署。

**建议的推进顺序**：先做一（仓库）与三（核心交互），这两步完成后工具就能日常使用；二、四的界面细节可以边用边调。

## 七、风险与应对

| 级别 | 风险 | 应对 |
| --- | --- | --- |
| 高 | **内存不足导致转写中断**：峰值 2.28 GB，空闲仅 2.5 GB | 界面启动时检查内存并提示；`batch_size_s` 已降至 150；必要时降至 100 |
| 高 | **会议录音与纪要误入版本库** | .gitignore 已覆盖；首次提交前逐项核对 `git status`；后续每次提交前确认 |
| 中 | 目标机器配置更低，跑不动 | 安装脚本做硬件检测并给出结论；ASR 支持切换轻量引擎 |
| 中 | 界面阻塞导致"假死" | 业务逻辑全部在后台线程；耗时操作均回报进度 |
| 中 | 更新代码后环境不匹配 | requirements 固定版本区间；提供升级脚本 |
| 低 | 杀毒软件误报 | 一级/二级分发方案不涉及自解压，风险很低 |
| 低 | 云端接口变更 | 已抽象为配置驱动，改配置即可切换 |

## 八、待决策事项

以下需要确认后才能进入实施：

1. **界面形态**：确认采用 PySide6 原生桌面窗口（推荐），还是有其他偏好？
2. **远程仓库**：Gitee 私有库 / 单位内网 GitLab / 其他？
3. **分发对象**：只自己用，还是要给同事？这决定是否要做便携包。
4. **目标机器**：后续要迁移的电脑配置如何（尤其是内存与是否有独显）？这决定是否要调整默认参数。
5. **是否启动 ASR 的 ONNX 化**：如果远期要做小体积 exe 或彻底解决内存瓶颈，这是个独立课题，需要评估。
